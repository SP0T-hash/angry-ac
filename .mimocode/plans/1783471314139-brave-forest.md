# Plano: Documentação SDD do Projeto VEMAPI SITE

## Contexto

O projeto VEMAPI SITE é uma plataforma de confiança digital e certificação que contém dois sistemas principais:

1. **VEMAPI SITE (Root)**: Aplicação Next.js 16 com landing page, módulo AC ANGRY (emissão de certificados digitais), portal de admin/usuário, e APIs serverless
2. **gs.vemapi (CORE-AR)**: ERP SaaS .NET 8 para Autoridades de Registro ICP-Brasil com módulos de identidade, checkout, ledger, billing e CRM

## Objetivo

Aplicar a metodologia Spec-Driven Development (SDD) do GitHub spec-kit para documentar o que está **efetivamente implementado** no projeto, criando specs que representem a verdade do sistema atual.

## Etapas do Plano

### Etapa 1: Criar estrutura de especificações
- Criar diretório `specs/` na raiz do projeto
- Criar subdiretórios para cada feature mapeada
- Criar o arquivo `constitution.md` com os princípios do projeto

### Etapa 2: Criar Constituição do Projeto
- Arquivo: `.specify/memory/constitution.md`
- Documentar princípios de arquitetura, segurança, conformidade (ICP-Brasil, LGPD)

### Etapa 3: Criar especificações por feature (baseado no que EXISTE)

- API SAF (serviço de assinatura)

#### Spec 007: CORE-AR - Motor de Pagamentos
- Checkout com webhooks

#### Spec 008: CORE-AR - Livro Razão e Split

#### Spec 011: Cyber Security (Status: Planned)

#### Spec 012: Infraestrutura Cloud (Status: Planned)

## Verificação

1. Cada spec deve descrever APENAS o que está implementado (a verdade)
2. User stories devem ser testáveis independentemente
3. Requisitos funcionais devem ser específicos e mensuráveis
4. Dados de entidades devem refletir o schema real do Supabase
5. Contratos de API devem corresponder aos endpoints existentes

## Decisões do Usuário

- **Escopo**: Sistema completo (AC ANGRY + CORE-AR + Landing Page)
- **Nível de detalhe**: Completo com user stories, requisitos funcionais, entidades de dados e contratos de API
- **Áreas de expansão**: Incluir como specs separadas (Cyber Security, Infraestrutura Cloud)

## Observações Importantes

- **As specs devem ser a verdade**: Não documentar funcionalidades que não existem
- **Brownfield**: Este é um projeto existente, não greenfield
- **Foco na realidade**: O que está implementado, não o que deveria estar
- **Conformidade**: Documentar conformidade com ICP-Brasil e LGPD onde aplicável
- **Expansões**: Funcionalidades "Em Expansão" viram specs com status "Draft" ou "Planned"
